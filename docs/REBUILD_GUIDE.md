코드가 아니라 "무엇을, 왜, 어떤 순서로" 만들지와 "다 만들었는지 확인하는 기준"을 적었습니다.

## 1. 전체 흐름과 마일스톤

```
약관 PDF ─▶ 텍스트 추출 ─▶ 구조화(규칙) ─▶ 구조 검증(규칙)
                                │
                                ▼
                          추출 묶음(규칙) ─▶ LLM 추출(OpenAI) ─▶ 근거 검증(규칙) ─▶ 정답 비교
                                                                     │
                                                    스키마 갭 분석(규칙) · 테이블 저장(SQLite)
```

원칙

- **구조화·검증·근거 확인은 LLM 없이 규칙으로.** 결과가 매번 같고, 줄 번호로 원문 위치를 되짚을 수 있어야 함.
- **LLM 은 판단이 필요한 추출에만.** LLM 결과의 모든 항목은 원문 인용과 숫자를 규칙으로 다시 확인.
- **실제 약관으로 검증.** 짧은 예시 텍스트로만 테스트하면 실제 PDF 에서 전부 깨집니다 (2026-11-09 에 실제로 그랬음:
  처음 파서는 예시 테스트를 다 통과했지만 실손 약관에서 조를 0개 찾음).

| 마일스톤 | 내용 | 완료 기준 |
|---|---|---|
| M1 | PDF 텍스트 추출 + 기본 구조화 (관·조·항·호·목·세목·부칙·별표) | 16.1 일반 약관 예시가 그대로 구조화됨 |
| M2 | 보험 약관 대응: 목차 건너뛰기, 두 줄 제목, 약관(part) 분리, 별표 닫기, 부록, 목차 조 정리 | 16.2 보험 약관 예시 + 실손 2605 에서 약관 10·조 173개 (15장). 실제 약관의 본문 별표는 괄호 없는 형태라 M3 에서 잡힘 (M2 에서는 별표가 거의 안 나와도 정상) |
| M3 | 편-조 번호, 보장종목, 줄바꿈 `다.`, 안내 상자, 각주, 번호 없는/괄호 없는 별표 | 15장 표의 조 수·약관 수와 같음 |
| M4 | 조항 인용 추출 + 구조 검증 | 7개 약관에서 검증 문제는 인터넷암보험 `제2조의9` 중복 1건뿐 (부칙 없음 info 제외) |
| M5 | 사고보장 스키마(실손) + 추출 묶음 + 근거 검증 | 실손 2605 묶음 8개, 13장 정답이 근거 검증 11/11 |
| M6 | LLM 추출 + 정답 비교 + 명령 | 실손 2605 《질병급여형》 추출 → 정답 비교 일치율 확인 |
| M7 | 스키마 갭 분석 (18장) | 실손 2605: 개념 16종, 정답 기준 36항·호 중 12 인용, 이유 8·2·14, 빈 필드 1 |
| M8 | 테이블 저장 (19장) | 실손 정답·전체 필드 예시를 저장 → 읽기 하면 원래와 같음, 실손 정답 70행 |
| M9 | 정액형: 별표 근거 + 암진단 정답 (20장) | 인터넷암보험 2404 정답 초안 근거 8/8 |

M1~M5, M7~M9 는 API 키 없이 만들고 테스트할 수 있습니다. M6 만 OpenAI 키가 필요합니다.
**해커톤 우선순위**: M1→M2→M3→M4→M5→M6(첫 실제 추출) 다음, 보험금 담당이 정액 계산을 시작하려면 M9, 발표용 차별점은 M7. M8 은 시간이 남으면.

권장 기술: Python 3.12, `uv`, `pydantic` v2, `pypdf`, `pytest`, `openai`. (2026-11-09 버전은 이 조합)

### 2.2 텍스트 추출

- `pypdf.PdfReader(path).pages` 의 `extract_text()` 를 `"\n"` 으로 이어 붙임. 20자 미만이면 스캔본으로 보고 에러.
- **pypdf 버전 고정: 7.0.0** (`uv add "pypdf==7.0.0"`). 모든 규칙과 3·15장 줄 번호·수치가 이 버전의 줄 모양 기준이고,
  리허설(2026-11-10)에서 7.0.0 으로 3.1 줄 번호(실손 2605 = 9,713줄, 1181·2803·7091번째 줄)가 그대로 재현됨.
- 큰 약관 하나에 **25~80초** 걸림 (PC 에 따라 다름. 리허설 PC 62~78초). PyMuPDF 는 훨씬 빠르지만 줄 모양이 달라 규칙을 다시 맞춰야 함.
  → 실제 PDF 테스트는 느리니 `pytest --pdf` 같은 옵션으로 기본 실행에서 빼기.
  → **추출 텍스트 캐시 권장**: 파일 해시를 키로, **bytes 로** 저장 (`write_text` 는 Windows 에서 줄바꿈을 바꾸고 `\r` 이 깨짐).
- 추출 텍스트 특징: 글자 사이 공백(`제 1 조`, `《 질 병급여형 》`), 단어 중간 줄바꿈(`…지급합니` / `다.`),
  쪽 번호 줄(`38`), 표가 평평해짐, 옆 상자 내용이 본문 중간에 끼어듦. 3장 참고.
- 정규화: `\r\n`/`\r` → `\n`, 전각 공백 `　`·`\xa0`·`﻿`(BOM) → 공백/삭제, 각 줄 `strip()`.
  **줄 나누기 = `\r\n|\r|\n` 으로 split, 줄 번호 = 인덱스 + 1** (원문 위치 되짚기. 3·15장 줄 번호가 이 기준).

## 3. 실제 약관 텍스트의 모양 (가장 중요)

실손 2605 기준. 줄 번호는 추출 텍스트 기준 (약 9,700줄).

### 3.1 문서 구성

| 줄 | 내용 | 처리 |
|---|---|---|
| 1~ | `보험약관`, 안내문, "약관 이용 가이드북" | 서문(preamble) |
| 70~120 | "약관의 핵심 체크항목": `제3조(보상내용)`, `제17조(청약의 철회)` … 줄만 나열 | 조처럼 보이지만 **안내** → 6.1 로 지움 |
| 994~1170 | 상품 목차·조항별 목차: `제 1 조 [보장종목] 5` (끝에 쪽 번호) | **목차** → 5.3 으로 건너뜀 |
| 1172 | `[별표 1] 용어의 정의 35` | 목차의 별표 줄 → 건너뜀 (안 건너뛰면 본문 전체가 별표가 됨!) |
| 1181 | `삼성 급여 실손의료비보장보험(2605)(갱신형, 무배당) 약관` (앞 줄은 쪽 번호 `4`) | **약관(part) 시작** |
| 1188~ | `제1 관 일반사항 및 용어의 정의` / `제 1 조 [보장종목]` … | 주계약 본문 |
| 1212 | `《 질 병급여형 》` | **보장종목** 구분 |
| 2803 | `비중증 비급여 실손의료비보장특약D(갱신형,무배당) 약관` | 다음 약관(특약). 조 번호 다시 1부터 |
| … | 특약 9개가 이어짐 (중증 비급여, 중지·재개, 지정대리청구 …) | |
| 7091 | `부록 약관에서 인용된 법령 내용 (가나다 순)` | **부록**: 법령 조문(`제 2 조(정의)`)이 이어짐 → 원문 보관 |

### 3.2 처음 파서가 실패한 방식 (같은 실수 피하기)

1. 조항별 목차의 `제 1 조 [보장종목] 5` 를 조로 읽음 → 목차 줄만 조 77개.
2. 목차의 `[별표 2] 보험금을 지급할 때의 적립이율 계산 38` 을 별표 시작으로 읽음 → **그 뒤 6,000줄(원문 62%)의
   실제 본문이 별표 하나에 들어가** 본문 조가 0개. 별표 안에서는 조를 안 찾기 때문.
3. 주계약 뒤에 특약 9개가 이어지는데 모두 `제1조`부터 다시 시작 → 조 번호 중복·순서 오류 수십 건.
4. 마지막 특약 뒤 부록의 법령 조문(`제 2 조(정의)`, `제 11 조(의사 등의 신고)`)을 약관 조로 읽음.

### 3.3 본문 안의 함정 (실제 예)

| 모양 | 실제 원문 | 올바른 해석 |
|---|---|---|
| 두 줄 괄호 제목 | `제 4 조의2 [‘기본형 실손의료비보장보험’에서` / `보상하지 않는 사항]` | 조 하나, 제목은 두 줄을 이은 것 |
| 줄 맨 앞 인용 | `…및` / `제2조의6(“대장점막내암”의 정의 및 진단 확정)에 따라 "초기유방암", …` | 새 조가 아니라 앞 항의 본문 |
| 줄바꿈된 문장 끝 | `…보험금을 지급합니` / `다. 다만, 조사가 필요한 때에는…` | `다.` 는 목 번호가 아님 |
| 쪽이 넘어간 문장 끝 | `…지급합니` / `109` / `다.` | 위와 같음 (쪽 번호 줄 무시) |
| 보장종목 | `《질병급여형》 제3조, 제4조` → `《상해급여형》 제3조, 제4조` → `제5조` | 보장종목마다 같은 번호의 조가 정상 |
| 편-조 번호 | `제2-1조의3 [“암” 등의 정의]`, 공통 `[특약 약관] 제1편 일반사항` 아래 `제1-1조` | 편 2, 조 1, 의 3 |
| 옆 안내 상자 | `용어` / `해설` / `<직업>` / `1. 생계유지…` / `2. "1"에 해당…` / `<직무>` / … / 본문 `2. 보험증권…` | 상자 안 1. 2. 는 호가 아님. 본문 호는 1 → 2 로 이어짐 |
| 상자 종류 | `설명 <「국민건강보험법」에 따른 본인부담금 상한제>`, `유의` / `사항` / `1. …`, `유의사항 1. 이 특약은…` | 모두 상자 |
| 표 아래 각주 | `㈜ 1. 보증지급횟수란…` / `2. 최소보증지급횟수 중…` / `3. …` / (상자) / `4. …` / 본문 `2. 중증간병연금` | 각주 번호는 호가 아님 |
| 괄호 없는 별표 | `별표1 악성신생물 분류표(초기유방암, … 제외)` | 별표 1 |
| 번호 없는 별표 | `별표 재 해 분 류 표`, `별표 보험금을 지급할 때의 적립 이율 계산` | 별표 (특약 마지막 조 뒤) |
| 평평해진 표 | `구 분 보 상 금 액` / `입원` / `(입원실료,` / … / `본인부담금(…)의 80%에 해당하는 금액` | 구조화 안 함, 본문 글로 둠 (LLM 이 읽음) |
| 상자가 낀 조 제목 | `제20조(계약내용의 변` / `설명 <해당 연도의 계약해당일이 없는 경우 예시>` / `계약일이 …` / `경 등) 제3항에 따라` | 인용 `제20조 제3항` |
| 원문 오타 | 인터넷암보험 고액치료비암진단특약Ⅱ: `제2조의9 [특약의 보장개시일]`, 바로 뒤 `제2조의9 [AJCC …]` | 검증이 잡아야 할 진짜 중복 (주계약은 같은 조항이 `제2조의10`) |

## 4. 구조화 데이터 모델

```
TermsDocument
├─ title: str            # 서문 첫 줄 (60자 이하)
├─ preamble: str         # 첫 구조 요소 이전의 본문
├─ parts: [TermsPart{title, line}]          # 약관 제목 줄 (주계약, ○○특약 …)

Heading.label: f"제{number}{kind} {title}"  (예: 원문 `제1 관 보험계약의 성립과 유지` → `제1관 보험계약의 성립과 유지`)

```

## 5. 파서: 줄 처리 순서와 규칙

**순서가 결과를 바꿉니다.** 한 줄씩 아래 순서로 처리합니다.

```
for 줄 in 정규화된 줄들:
  0. 괄호가 안 닫힌 조 시작 줄이면 다음 1~2줄과 이어 붙임 (5.2)
  1. 빈 줄 · 쪽 번호 줄 → 건너뜀
       쪽 번호 줄 = ^[-–—\s]*\d+\s*(/\s*\d+)?[-–—\s]*$|^-\s*\d+\s*-$   (38, 109, - 1 -, 3 / 20)
  2. 목차 줄 → 건너뜀 (5.3)
  3. 약관 제목 줄 → 새 약관(part) 시작 (5.4)  ※ 0에서 이어 붙인 줄은 제외
  4. 부록 안이면: '제1관/제1장/제1편' 이 나오면 부록 닫기, 아니면 부록에 붙이고 다음 줄 (5.6)
  5. 부록 시작 줄 → 부록(별표처럼) 시작
  6. 부칙 줄 → 부칙 시작
       부칙 줄 = ^부\s*칙\s*(?:[<〈(\[［【].*)?$   (부칙, 부 칙, 부칙 <2024.1.1.>)
       부칙 번호를 1 올리고 현재 조·항·별표를 닫음. 이후의 조는 부칙 조(`부칙 제1조`).
       부칙은 다음 부칙 줄이나 새 약관 제목 줄(5.4, 부칙 번호 0 으로)에서만 끝남. 부칙 안에서는 관 제목을 무시.
  7. 별표 시작 줄 → 별표 시작 (5.5)
  8. 별표 안이면: 본문 재개 줄이면 별표 닫기, 아니면 별표에 붙이고 다음 줄 (5.5)
  9. 관·장·절·편 제목 (부칙 안이 아닐 때) → 제목
 10. 보장종목 구분 줄 《…》 → 보장종목 시작 (5.8)
 11. 조 시작 줄 → 조 시작 (5.1)
 12. 그 밖 → 조 본문 한 줄 (5.9: 줄바꿈 다., 상자, 각주, 항·호·목·세목, 이어지는 글)
```

### 5.1 조 시작 줄

```
ARTICLE = ^제\s*(?:(?P<vol>\d+)\s*-\s*)?(?P<num>\d+)\s*조(?:\s*의\s*(?P<sub>\d+))?\s*(?P<rest>.*)$
OPEN    = { ( → ),  [ → ],  【 → 】,  〔 → 〕,  ［ → ］,  < → > }
```

- `rest` 가 여는 괄호로 시작하고 닫히면 → 제목 = 괄호 안, 본문 = 괄호 뒤.
  같은 종류 괄호가 제목 안에 또 있으면(`제28조(…부활(효력회복))`) **깊이를 세서** 짝이 맞는 닫는 괄호를 씀
  (기준 구현은 첫 닫는 괄호를 써서 제목이 `…부활(효력회복` 이 됐음. 조 수에는 영향 없음).
- **5.2 로 이어 붙인 뒤에도 괄호가 끝내 안 닫히면 조가 아님** (본문 한 줄로 처리). 예: 상자가 낀 `제20조(계약내용의 변`.
  아래 '괄호 제목이 없으면' 규칙으로 넘기면 `(계약내용의 변` 이 25자 이하라 가짜 조가 됨.
- **괄호 제목 뒤가 인용 표시면 조가 아님** (줄 맨 앞 인용):
  `^(에|의|및|와|과|를|을|로|으로|부터|까지|에서|[,、]|제\s*\d+\s*(항|호))`
  - `이` 는 넣지 말 것: `제1조(목적) 이 약관은…` 는 조.
- 괄호 제목이 없으면:
  - `rest` 가 비었거나, 동그라미 숫자(①)로 시작하거나, `삭제`로 시작 → 조 (제목 없음).
  - `rest` 가 25자 이하이고, 조사(`에의및와과를을는은이가로으부까도만`)로 시작하지 않고, `.` 로 끝나지 않고,
    `제` 나 숫자로 시작하지 않으면 → `제1조 목적` 처럼 괄호 없는 제목.
  - 그 밖 → 본문 속 인용 (`제3조에 따라 처리한다.`). 조 아님.
- `삭제` 제목 또는 본문이 `삭제`로 시작하면 `deleted=True`.
- 조 시작 시 상위 제목 경로(path), 현재 부칙 번호, 현재 약관(part), 현재 보장종목(section)을 붙임.
- 본문이 있으면 그 줄을 5.9 처럼 본문으로 처리.

### 5.2 두 줄로 끊긴 괄호 제목

조 시작 줄의 `rest` 가 여는 괄호로 시작하는데 닫는 괄호가 없으면, **다음 내용 있는 줄 하나**(빈 줄은 최대 1줄 건너뜀,
즉 최대 2줄 아래까지 봄)가 `^[^\[\]【】〔〕［］]*[\]】〕］)]\s*(.*)$` (닫는 괄호가 있는 줄)이면 공백 하나로 이어 붙여 한 줄로 처리.
그 줄이 닫는 괄호 줄이 아니면 이어 붙이지 않음 (세 줄짜리 제목은 지원 안 함. 실제 7개 약관에 없음).
이어 붙인 줄은 그 뒤 판단(목차 줄 포함)에 그대로 씀. **줄 번호는 첫 줄 것.** 이어 붙인 둘째 줄은 다시 처리하지 않음.

### 5.3 목차 줄 (건너뜀)

- 조 시작 줄인데 제목(괄호)이 있고 본문이 `^\d{1,3}$`(쪽 번호만) → 목차.
  예: `제 1 조 [보장종목] 5`, 이어 붙인 `제 4 조의2 [‘기본형…에서 보상하지 않는 사항] 13`
- 괄호가 열리고 닫힌 별표 줄인데 괄호 뒤가 `^\S.*\s\d{1,3}$` → 목차. 예: `[별표 1] 용어의 정의 35`
  - 쪽 번호가 글자에 붙은 목차 줄도 있음: 인터넷암 2404 `[별표 12] 보험금을 지급할 때의 적립 이율 계산52`.
    부록처럼 `\D\s?\d{1,3}$` 로 끝나는 것도 목차로 봐도 됨 (기준 구현은 못 걸렀지만, 곧 약관 제목 줄에서 닫혀 해는 없었음).
- 관·장 제목 줄인데 제목이 `^\S.*\s\d{1,3}$` → 목차.
- 부록 줄인데 내용이 `^\S.*\s\d{1,3}$` 이거나 `\D\s?\d{1,3}$` 로 끝남 → 목차. 예: `[부록]약관에서인용된법령내용 41`
- **쪽 번호가 없는 목차 줄**(`제 1 관 일반사항`, 핵심 체크항목의 `제3조(보상내용)`)은 여기서 못 거르고 6장 후처리로 지움.

### 5.4 약관(part) 제목 줄

- 일반 형태: `^\S.{1,80}\s?약관$`, 90자 이하.
  예: `지정대리청구서비스특약 약관`, `삼성 인터넷암보험(2404)(갱신형,무배당) 고액치료비암진단특약Ⅱ 약관`
- 제외:
  - 공백·문장부호를 지운 값이 `약관 / 보험약관 / 주계약약관 / 특약약관 / 제도성특약약관` (표지·목차 분류 이름)
  - 숫자·동그라미 숫자·`ㆍ∙·-` 로 시작
  - 괄호 안을 지운 뒤 `, “ ” " ' ‘ ’` 또는 `에서`, `할 때` 포함 (문장이 줄바꿈된 것.
    예: `반대로 피보험자에게 발생(진단)된 사고가 제9차 개정 한국표준질병ㆍ 사인분류를 적용할 때, 약관`)
  - 조·관·별표 시작 줄
- **문맥 조건 (필수)**: **바로 앞의 내용 있는 줄 하나**(빈 줄은 최대 4줄까지 건너뜀)가 쪽 번호 줄이거나,
  **바로 다음의 내용 있는 줄 하나**(빈 줄은 최대 4줄까지 건너뜀)가 `^(※|제\s*1\s*(관|장|편|조))`.
  특약은 새 쪽에서 시작하고 바로 `※ 이 특약은…` 안내가 오기 때문.
  - "4줄 안의 아무 줄" 로 읽으면 안 됨: 16.1 의 첫 줄 `위드갓 서비스 이용약관` 이 (두 줄 뒤 `제1장 총칙` 때문에) 약관 제목이 되어 문서 제목을 잃음.
- 공통 일반사항: `^\[(?:주계약|특약)\s*약관\]\s*(제\s*\d+\s*편\s*\S.{0,30})$` + 위 문맥 조건 → 약관 제목.
  예: `[특약 약관] 제1편 일반사항`. 특약 안의 안내 문장
  `[특약 약관] 제1편 일반사항 제1-1조부터 제1-15조까지의 규정을 이 특약 제1편 일반사항으로 합니다.` 은 30자를 넘어 제외됨.
- 새 약관 시작 시: 상위 제목 경로, 현재 조·항, 별표, 부록, 보장종목, 부칙 번호를 모두 초기화.

### 5.5 별표

```
APPENDIX = ^([\[【〔<［(])?\s*(별\s*표|별\s*지)\s*(\d*)\s*([\]】〕>］)])?(.*)$
```

- 괄호 있는 형태 `[별표 1] 제목`, `【별지 1】` → 별표. (닫는 괄호 없고 번호 없고 뒤가 바로 글자면 아님)
- 괄호 없고 번호 있음 `별표1 악성신생물 분류표(…)`: 원문이 `^별\s*[표지]\s*\d+\s+\S` (번호 뒤 공백)여야 하고,
  내용이 조사로 시작하지 않고, `.` 로 끝나지 않고, 80자 이하. (`별표1에 따른`, `별표1 에서 정한` 은 인용)
- 괄호 없고 번호 없음 `별표 재 해 분 류 표`: 원문이 `^별\s*[표지]\s+\S`, 조사 시작 아님, `.` 끝 아님, **40자 이하**.
- 라벨: `별표 1 제목` (종류 공백 제거 + 번호 + 나머지).
- 별표 안의 줄은 구조화하지 않고 별표 원문에 붙임. **단, 본문 재개 줄이 나오면 별표를 닫고 그 줄을 정상 처리**:
  - `편·장·관` 제목 줄, 또는
  - 괄호 제목이 붙은 조 시작 줄 (`제1조 [특약의 체결 및 소멸]`). 주계약 별표 뒤에 특약 본문이 이어지는 경우.

### 5.6 부록

- `^[\[【]?\s*부\s*록\s*[\]】]?\s*(\S.*)$` (뒤에 제목 필수) → 라벨 `부록 <제목>` 인 별표로 시작, **부록 모드**.
- 부록 모드에서는 조 시작 줄도 본문 재개로 보지 않음 (법령 조문 `제 2 조(정의)` 가 이어지므로).
  `제1관/제1장/제1편`(번호 1) 제목이 나오거나 새 약관 제목 줄이 나와야 닫힘.
- 목차의 `[부록] 약관에서 인용된 법령 내용`(쪽 번호 없음, 실손 2605 1003번째 줄)도 부록으로 시작됨. 이 부록은 약관 제목 줄이 아니라
  **목차의 첫 `제 1 관` 제목**에서 닫히는데, 그 사이의 상품 목차·상황별 목차(약 1,000자)를 먹어서 200자 기준(6.3 첫 규칙)으로는
  안 지워짐 → **6.3 둘째 규칙**으로 지움. 부록을 닫는 `제1관` 줄은 그대로 이어서 관 제목으로 처리.

### 5.7 관·장·절·편 제목

`^제\s*(\d+)\s*(편|장|절|관)(?:\s+(.*))?$`, 제목 40자 이하이고 `.` 로 끝나지 않을 때. 부칙 안에서는 무시.
제목 시작 시 같은 수준 이하의 제목을 경로에서 빼고 추가, 현재 조·항 초기화, **보장종목 초기화**.

### 5.8 보장종목

`^《\s*([^》]{1,30}?)\s*》$` → 공백을 모두 지운 이름(`《 질 병급여형 》` → `질병급여형`)을 현재 보장종목으로.
현재 조·항 초기화 (구분 줄은 앞 조 본문에 붙이지 않음). 관 제목·약관·별표 시작 시 초기화.

### 5.9 조 본문 한 줄

조 밖(현재 조 없음)이면: 별표 안 → 별표 원문, 부칙 안 → 부칙 본문(`addendum_text`), 그 밖 → **서문(preamble)** 에 붙임.
약관 제목 줄 바로 뒤의 `※ 갱신주기는 1 년으로 합니다.` 나 관 제목과 첫 조 사이 글도 서문으로 감 (기준 구현 방식. 버려도 수치에는 영향 없음).
조 안이면 아래 순서.

1. **줄바꿈된 문장 끝**: 바로 앞 원문 줄(빈 줄·쪽 번호 줄 건너뛰고 최대 5줄 앞)이 `니` 로 끝나고 이 줄이 `^다\.` → 이어지는 글.
2. **안내 상자 시작**: 이 줄이 `^(용어\s*해설|설명|유의|유의사항)(\s*<.*>)?$` 또는 `^(유의사항|참고사항)\s+\d{1,2}\.\s`,
   또는 바로 앞 줄이 `용어` 이고 이 줄이 `해설` → 상자 시작 (상자 안 번호 {항:0, 호:0, 목:0}).
3. **각주 시작**: `^(?:㈜|\(주\)|주\))\s*(?:(\d{1,2})\.)?` → 상자처럼 시작하되 상자 호 번호 = 그 숫자(없으면 0). 이 줄은 글로 붙이고 끝.
4. **상자 안이면** (5.10) 상자 줄로 처리하고 끝, 상자가 끝났으면 계속.
5. 동그라미 숫자로 시작 → 새 항 (번호, 나머지 글). 호·목·세목 초기화.
6. 호 `^(\d{1,2})\.(?!\d)\s*(.*)$` / 목 `^([가나다라마바사아자차카타파하])\.\s*(.*)$` /
   세목 `^(\(\d{1,2}\)|\d{1,2}\))\s*(.*)$` → 항목. 부모: 호는 항, 목은 현재 호, 세목은 현재 목 또는 호.
   항이 없으면 번호 없는 항을 만들어 붙임.
7. 그 밖 → 마지막 요소(항·항목)의 글에 줄바꿈으로 이어 붙임.

### 5.10 안내 상자 끝 판단

상자는 끝 표시가 없어서 **번호로 판단**합니다.

- 상자 안 `<…>` 소제목 줄 → 상자 안 번호를 모두 0 으로 (다시 셈).
- 상자 안 줄이 항(①)·호(1.)·목(가.) 표시로 시작하면 번호 n 에 대해:
  - n 이 **본문(상자 밖)이 기다리는 다음 번호**이고 **상자 안의 다음 번호(상자 번호+1)가 아니면 → 상자 끝**. 그 줄은 본문으로 처리.
    - 본문 다음 항 = 조의 마지막 번호 있는 항 + 1, 본문 다음 호 = 현재 호 + 1 (없으면 1), 목도 같은 방식.
  - 아니면 상자 안 번호로 기록 (항이면 호·목 0, 호면 목 0)하고 글로 붙임.
- 조·관·약관·별표·보장종목이 시작되면 상자도 끝.
- 상자 내용은 버리지 말고 앞 요소의 글로 붙임.
- 한계: 상자 안 ①② 뒤에 본문 ③ 이 오면 구분 못 함 (실제 7개 약관에는 없음).

검증 예 (실손 제13조): 본문 `1.` → 상자 `<직업>` `1.`(상자1) `2.`(상자 다음=2, 본문 다음=2 → 상자 유지) `<직무>`(상자 0) →
본문 `2.`(본문 다음=2, 상자 다음=1 → **상자 끝**) → `3.` `4.` → 항 `②` → 상자 `설명 <…>` → 본문 `③`(상자 다음=1 → 끝).

## 6. 파서: 후처리 (문서를 다 읽은 뒤)

### 6.1 목차·안내에서 잡힌 조 지우기

글자 수 = `full_text()` 길이. 조 A 를 지우는 조건 (둘 중 하나):

1. A 가 200자 미만이고, 뒤에 같은 라벨이고 제목이 같은(공백·문장부호 무시, 한쪽이 다른 쪽으로 시작해도 같음, 한쪽 제목 없으면 같음)
   조 B 가 있고, B 의 글자 수 ≥ max(2×A, A+40), 그리고 (A.part 가 None 이거나 A.part == B.part).
   - `A.part == B.part` 조건: 서로 다른 특약의 같은 번호 짧은 조를 지우지 않기 위해.
2. 문서에 약관(part)이 있고, A 가 첫 약관 제목 줄 앞(part None)이고 제목이 있고, 뒤에 part 가 있는 같은 라벨·**정확히 같은 제목** 조가 있음.
   - 안내 페이지의 마지막 조는 뒤따르는 안내문 전체를 본문으로 먹어서 길어지므로 길이를 보지 않음.

### 6.2 빈 관 제목 지우기

관 제목 H 아래(H 의 줄 번호 < 조 줄 번호 < **바로 다음 제목(종류 무관)의 줄 번호**)에 남은 조가 하나도 없고,
뒤에 같은 종류·번호·제목의 관 제목이 있고 (H.part 가 None 이거나 같은 part) → 지움. 장·편·절도 같은 규칙.

### 6.3 목차에서 잡힌 별표·부록 지우기

1. 별표 X 의 글이 200자 미만이고, 뒤에 제목이 같은 더 긴 별표가 있으면 지움.
2. **문서에 약관(part)이 있고 X 가 part None(첫 약관 제목 줄 앞)이며, 뒤에 part 가 있는 같은 제목의 별표·부록이 있으면 길이와 상관없이 지움.**
   (5.6 의 목차 `[부록]` 처럼 목차를 먹어 길어진 경우. 리허설에서 추가한 규칙. 기준 구현에는 없어서 실손 2605 등 큰 약관 5개에
   목차 부록이 1개씩 남아 있었음 → 15장의 별표·부록 수는 이 규칙을 쓴 값)

제목 비교: 공백·문장부호를 무시하고 비교하되, **별표 번호는 정확히** 비교 (`별표\s*(\d+)`. 글자 앞부분 비교만 하면 `별표 1` 이 `별표 10…` 과 같아짐).

### 6.4 빈 약관 지우기

조도 관 제목도 없는 약관(part)은 지우고 나머지 번호를 다시 매김 (조·관의 part 도 고침).
조는 없는데 관 제목은 있는 약관은 남겨서 검증(`PART_WITHOUT_ARTICLES`)으로 알림.

### 6.5 서문·제목

서문의 내용 있는 첫 줄이 60자 이하면 문서 제목으로 쓰고 **그 줄은 서문에서 뺌** (16.1 기대: 서문은 `이 약관은` 으로 시작).
마지막으로 모든 조의 인용을 추출 (7장).

## 7. 조항 인용 추출 (`full_text()` 대상)

```
REF_TITLE = [(（](?:[^()（）]|[(（][^()（）]*[)）]){1,200}[)）]       # 조 제목 괄호, 한 겹 중첩, 200자(상자 낌 대비)
REF       = (?:《\s*([^》]{1,30}?)\s*》\s*)?                       # 보장종목
            제\s*(?:(\d+)\s*-\s*)?(\d+)\s*조(?:\s*의\s*(\d+))?       # 편-조, 조, 의
            (?:\s*REF_TITLE)?
            (?:\s*제\s*(\d+)\s*항)?(?:\s*제\s*(\d+)\s*호)?
PARA_REF  = 제\s*(\d+)\s*항                                         # 조 없이 항만
EXTERNAL  = (」|』|｣|(?<!방)법|법률|령|규칙|규정|조례|협약|고시)\s*$   # 앞이 법령 이름
CONNECT   = ^(?:\s|[,·ㆍ~～\-]|및|또는|부터|에서|내지|와|과)*$          # 범위·나열 연결어
```

1. REF 매치와 (REF 매치 범위 밖의) PARA_REF 매치를 위치 순으로 정렬.
2. 직전 인용과의 사이 글이 CONNECT 에 맞으면 "이어짐".
3. 조 인용: 앞 40자를 **줄바꿈을 공백으로 바꿔서**(법령 이름이 앞 줄에 있을 수 있음) EXTERNAL 검사.
   다른 법령이거나, 이어짐이면서 직전 인용이 다른 법령이면 → 제외. 아니면 인용 추가.

   아니면 같은 조(article=0). 직전이 다른 법령이면 제외.

## 8. 구조 검증

| 코드 | 수준 | 내용 |
|---|---|---|
| `NO_ARTICLES` | error | 조가 하나도 없음 (이것만 내고 끝) |
| `HEADING_DUPLICATE` / `HEADING_NUMBER_GAP` | warning | 관 번호 중복 / 이어지지 않음 |
| `PART_WITHOUT_ARTICLES` | warning | 약관 제목은 있는데 조가 없음 |
| `ARTICLE_DUPLICATE` | error | 같은 번호의 조가 여러 번 (한 번만 보고) |
| `ARTICLE_NUMBER_GAP` | warning | 조 번호 건너뜀 (메시지 예: `제2-2조가 없습니다.`) |
| `ARTICLE_ORDER` | warning | 앞 조보다 번호가 작음 |
| `ORPHAN_SUB_ARTICLE` | warning | `제N조의M` 은 있는데 `제N조` 없음 |
| `MISSING_TITLE` | info | 제목 없는 조 (부칙 제외) |
| `EMPTY_ARTICLE` | warning | 본문 없는 조 |
| `MIXED_PARAGRAPHS` / `PARAGRAPH_NUMBER_GAP` | warning | 번호 있는·없는 항 섞임 / 항 번호가 1,2,3… 아님 |
| `ITEM_NUMBER_GAP` | warning | 호·목·세목 번호가 1,2,3… / 가,나,다… 아님 |
| `BROKEN_REFERENCE` | error | 인용한 조·항·호가 없음 |
| `REFERENCE_TO_DELETED` | warning | 삭제된 조 인용 |
| `NO_ADDENDUM` | info | 부칙 없음 (보험 약관은 보통 없음) |

규칙

- **조 번호 검사 단위**: (약관 part, 부칙 번호, 편 volume) 마다 따로. 메시지 앞에 약관이 여러 개면 `[약관 제목] `.
- **중복 키**: (번호, 의, **보장종목**). 보장종목이 다르면 같은 번호여도 중복 아님.
- **순서 검사 (보장종목 가지)**: 번호 있는 조(의 없는 조)를 차례로 보면서
  - 보장종목 없음 → 있음: 지금 기대 번호를 "가지 시작" 으로 저장
  - 보장종목 A → B: 기대 번호를 가지 시작으로 되돌림
  - 보장종목 있음 → 없음: 기대 번호를 지금까지 본 최대 번호 다음으로
  - 번호 > 기대 → GAP, 번호 < 기대-1 → ORDER, 기대 = max(기대, 번호+1)
  - 예: 제1, 제2, 《질병》제3, 제4, 《상해》제3, 제4, 제5 → 문제 없음
- **관 번호**: 약관(part)이 바뀌면 처음부터. 하위 제목은 상위 제목마다 1부터 또는 문서 전체에서 이어서, 둘 다 정상.
- **인용 대상 찾기**: 키 (편, 조, 의). 같은 약관 → 다른 약관 순. 후보가 여럿이면 인용의 보장종목,
  없으면 인용한 조의 보장종목과 같은 조. 부칙 안 인용은 같은 부칙 → 본문 순.
  - 항: 대상 조의 항 번호에 있어야 함. 항 표시가 없는 조는 본문 전체가 제1항.
  - 호: 그 항(또는 모든 항 중 최대)의 호 개수 이하.

```
Product{name, insurer, version, coverages[], coverage_codes[]}
Coverage{id, name, kind: main|rider, risks[], exclusions[], source?}          # 보장 = 약관 하나
Risk{id, claim_reason, coverage_code?, section?, rules[]}                     # 청구사유 × (담보코드)
  claim_reason: diagnosis|surgery|hospitalization|outpatient|death|disability|other
BenefitRule{id, name, insured_role, policy_status?, conditions, special_conditions[],
            benefit, installment?, source, extra_sources[], status: confirmed|needs_review}
RuleConditions{exemption_days?, reduction{days, ratio}?, deductible_days?, occurrence?,
               limit{per_event_days?, total_days?, count?, amounts[AmountLimit]},
               facility?, extension{days, max_visits?, max_visit_days?}?}   # 통원 한도: '90회' → max_visits, '90일' → max_visit_days
AmountLimit{amount(원), per: visit|day|stay|year|daily_average|event, selectable}
Benefit{type: rate|fixed|actual_cost, base: sum_insured|premium_paid|reserve|medical_cost,
        ratio{numerator, denominator}?, fixed_amount?, min_amount?, max_amount?,
        cost_type: covered|non_covered|room_difference ?, deductible?, copay_cap_annual?}

SpecialCondition{type, related_rule_id?, description}
Exclusion{id, kind: kcd|cost_item|cause, description, coverage_code?, exception, section?, source, status}
CoverageCode{code, name, kcd[KcdRange{start, end, level?, kcd_version?, valid_from?, valid_to?}], source?}
SourceRef{part, section?, article?, paragraph?, item?, appendix?, quote}     # article 또는 appendix 필수
```

검사 (pydantic validator)

- 비율 분모 > 0. `type=rate` 면 ratio 필수, `fixed` 면 fixed_amount 필수, `actual_cost` 면 ratio 나 deductible 필수.
- Deductible 은 amounts·ratios·copay_rate 중 하나는 있어야 함. 면책기간 ≤ 감액기간.
- KCD 형식 `^[A-Z]\d{2}(\.?\d{1,2})?$` (C50, C50.1, C501), start ≤ end (점 빼고 비교).
- Product: 규칙·제외 id 중복 금지, risk/exclusion 의 coverage_code 는 coverage_codes 에 있어야 함, related_rule_id 존재.

## 10. 추출 묶음 (LLM 에 한 번에 보낼 단위)

- 대상 약관: 조 중에 보장종목이 있거나, 제목이 `보상\s*내용|보험금의\s*지급\s*사유|보상하는\s*사항` 인 조가 있는 약관.
  (중지·재개, 지정대리청구, 장애인전환, 특별조건부 같은 제도성 특약은 자동으로 빠짐)
- 첫 대상 약관은 `main`, 나머지는 `rider`.
- 묶음 = 약관 × 보장종목. 보장종목 없으면 약관 하나 = 묶음 하나 (보장 조만).
- 묶음의 조 = 그 보장종목의 조 + 그 조들이 인용한 같은 약관의 **보장종목 없는** 조(제5조 한도) +
  보장 조와 (편, 번호)가 같은 보장종목 없는 `제N조의M`(제4조의2). 원문 순서로.
- 렌더링 (프롬프트 본문):
  ```
  약관: <약관 제목>

  보장종목: <보장종목>

## 11. LLM 추출

- **id 는 코드가 다시 매김** (LLM id 는 버림): 접두어 `p<약관번호>/<보장종목, 공백·기호 제거>`

## 12. 근거 검증 (LLM 없음)

| 코드 | 수준 | 내용 |
|---|---|---|
| `SOURCE_NOT_FOUND` | error | source 의 약관·보장종목·조(또는 별표)가 구조화 결과에 없음 |
| `PARAGRAPH_NOT_FOUND` | warning | 그 조에 그 항이 없음 (항 표시 없는 조는 제1항 허용) |
| `QUOTE_NOT_FOUND` | warning | 인용문이 그 조 원문에 없음 |
| `NUMBER_NOT_FOUND` | warning | 규칙의 숫자가 근거 조들(source + extra_sources) 원문에 없음. **주 근거 조를 못 찾으면 숫자 검사 안 함** |

- 비교 정규화(squash): `[\s"'“”‘’`·∙ㆍ･]+` 를 모두 지움. 인용문 squash 가 조 `full_text()` squash 의 부분 문자열이면 OK.
- 약관 찾기: squash 값이 같은 약관 → 아니면 한쪽이 다른 쪽을 포함하는 약관이 하나뿐일 때. 약관 없는 문서는 part None.
- 조 찾기: 그 약관에서 라벨 squash 일치 → 보장종목이 있으면 같은 보장종목, 없으면 보장종목 없는 조 우선.
- 원문 숫자 읽기 (squash 한 글에서):
  - 금액 `(\d+(?:,\d{3})*)(억|천만|백만|십만|만|천)?원` → 숫자 × 단위 (`5천\n만원` → 50,000,000, `1 만원` → 10,000)
  - 퍼센트 `(\d+(?:\.\d+)?)%`, 일 `(\d+)일`, 회 `(\d+)회`
- 확인할 숫자: 보상률(분자/분모×100), 지급금액, 자기부담 연간 상한, 공제 정액·비율, 금액 한도, 연장 일수·통원 횟수, 면책·감액 일수.
- 문제 없으면 `confirmed`, 하나라도 있으면 `needs_review`. **confirmed = 원문 근거 있음** (업무 검토 완료 아님).
- 담보코드 source 도 같은 방식으로 확인 (문제만 보고).
- **별표 근거**(`appendix` 만 있는 source): 별표 번호는 약관마다 1부터라 `source.part` 약관의 범위(약관 제목 줄 번호 ~
  다음 약관 제목 줄 번호) 안에서 찾고, 번호를 **정확히** 비교 (`별표\s*(\d+)`; 글자 포함 비교는 `별표1` 이 `별표 10`
  에 맞음). 별표도 인용문을 확인하고 별표 원문을 숫자 확인에 씀 (정액형 지급 금액은 별표1 에 있음, 20장).
- 기간 `(\d+)년(?:이내|이후|초과|간|동안|이 ?지|이되|단위)` 는 N×365 일로도 읽음 (`1년 이내` ↔ 감액 365일). 날짜 `2026년` 제외.

## 17. 알려진 한계 (2026-11-10 기준)

- 사고보장 추출은 **실제 LLM 으로 한 번도 돌려보지 않음**. 첫 실행 결과를 보고 프롬프트를 다듬어야 함.
- 정답은 《질병급여형》만. 《상해급여형》·비급여 특약으로 늘리면 평가 범위가 넓어짐.
- 평평해진 보상금액 표를 LLM 이 헷갈릴 수 있음 → 근거 검증의 NUMBER_NOT_FOUND 와 정답 비교로 드러남.
- 정액형(암보험)은 지급 금액이 별표에 있음 → 묶음에 인용된 별표와 정의 조(`제2조의N "암"의 정의`)를 넣어야 함.
- 상자 끝 판단 한계 (5.10), 번호 없는 `(주)` 바로 뒤 본문 `1.` 은 각주로 볼 수 있음.
- 보장종목 구분은 다음 관에서 끝 → 공통인 `제4조의2` 가 앞 보장종목(상해급여형)에 붙음 (검증 영향 없음).
- 암치료플러스종신보험 인용 1건은 PDF 추출 때 상자가 조 제목 괄호에 끼어 생김 (REF_TITLE 200자로 해결했지만 같은 유형이 더 있을 수 있음).
- 보상 제외의 예외(`다만 F20~F29 요양급여는 보상`)는 `exception` 글로만 둠.
- 개정 비교(2601 ↔ 2605)는 설계만: 둘 다 추출해서 규칙 id 기준 diff. 테이블 저장(19장)에 두 상품을 넣으면 SQL 조인으로 비교 가능.
- 갭 분석이 제안한 스키마 확장(합산 한도, 1회 산정 규칙 등 16종)은 스키마에 아직 반영하지 않음.
- 갭 분석 개념 목록은 실손 2605 문구 기반. 암보험 등 다른 약관의 새 개념은 '근거 없는 원문 · extraction_gap' 으로 드러나니 보고 추가.
- 정액형 묶음은 아직 조(제3조)만 넣음 → LLM 추출 전에 묶음에 인용된 별표·정의 조(제2조의N)를 넣는 확장 필요 (20장).

## 18. 스키마 갭 분석 (M7, LLM 없음)

목적: 추출 결과가 스키마에 **잘 들어간 것**만 보면 스키마가 표현하지 못해 버려진 내용이 보이지 않음. **약관 원문에서
출발**해 데이터로 담지 못한 것을 찾고 스키마 확장을 제안. 결과는 LLM escalations 와 같은 형식([TEAM_INTERFACE.md](TEAM_INTERFACE.md) ③).

**원문 단위**: 묶음의 조를 항·호로 나눔. 호가 있는 항은 항 본문(머리글)과 호를 따로. 호 텍스트는 하위 목까지 이어 붙임.
공통 조(보장종목 없는 제5조 등)는 여러 묶음에 들어가지만 (약관, 보장종목, 조, 항, 호) 키로 **한 번만** 보고하고 묶음 목록을 기록.

**개념 목록** (패턴은 squash 한 글에 적용, 하나라도 맞으면 그 항·호에 개념이 있음):

| 코드 | 종류 | 개념 | 패턴 | 제안 |
|---|---|---|---|---|
| SHARED_LIMIT | 구조 | 합산 한도 | `합산하여\d[\d,]*(?:억\|천만\|백만\|만\|천)?원(?:이내\|한도)`, `보상금액을합산` | `LimitPool{amount, per, members}` |
| COUNTING_RULE | 구조 | 1회 산정 규칙 | `(?:통원)?1회로보[아고]`, `1회의통원으로보아`, `각(?:치료\|진단)행위를1회로` | `CountingRule{unit, merge_when, deductible_on_merge}` |
| EVENT_DEFINITION | 구조 | 사고 단위 정의 | `[“"]?하나의질병[”"]?이란`, `1회입원이라함은` | `EventDefinition` |
| STAGED_LIMIT | 구조 | 단계적 보장 | `최초\d+회보장하고`, `\d+회단위로` | `Limit.stages` |
| ROUTING | 구조 | 다른 보장종목으로 이관 | `《[^》]+》제\d+조\(보상내용\)(?:또는《[^》]+》제\d+조\(보상내용\))?에서보상` | `redirect_to` |

| CONTRACT_HISTORY | 필드 | 갱신·전환·재가입 | `자동갱신`, `재가입` | `Condition.contract_history` |
| ELIGIBILITY | 필드 | 대상 질환 조건 | `산정특례` | `Risk.eligibility` |

| STRUCTURED_EXCEPTION | 부분 | 보상 제외의 예외 (보상하지 않는 사항 조만) | `\(다만,[^)]*보상` | `ExclusionException{kcd, cost_type, insured_condition, age_limit}` |

**근거 없는 원문** (사고보장 데이터가 있는 묶음만 — 규칙·제외의 source.part·section 이 묶음과 같음):
- 안내 문장 제외: 호가 아닌 단위 중 squash 길이 < 80 이고 `다음(?:과같|의|에)` 가 있는 것 ('회사는 다음의 … 보상하지 않습니다').
- 인용됨 = 그 묶음 데이터의 인용문(source·extra_sources, squash) 하나라도 그 단위 squash 의 부분 문자열.
- 인용 안 된 단위의 이유:
  1. `schema_gap`: 그 단위에 구조·필드 종류 개념이 있음 → 스키마 확장
  2. `uncited_value`: 그 단위의 숫자(12장 숫자 읽기)가 그 묶음 규칙의 확인할 숫자와 같음 → 근거 인용 보완
  3. `extraction_gap`: 나머지 → 지금 스키마로 담을 수 있는데 데이터에 없음 → 추출·정답 보완

**빈 필드**: 데이터가 있는 묶음에 KCD_VERSION 이 있는데 담보코드 `kcd_version` 이 모두 비어 있음 / ANNUAL_COUNT 가 있는데 `Limit.count` 가 없음.

**완료 기준 (실손 2605 + 13장 정답)**: 개념 16종 모두 나옴 (구조 5 · 필드 8 · 부분 3, 원문 128곳), 《질병급여형》 단위 36개 중
인용 12, 이유 schema_gap 8 · uncited_value 2 (제3조 ③④, 180일·90회) · extraction_gap 14, 빈 필드 KCD_VERSION 1건.
schema_gap 8곳: 제3조 ②2.(감면) ⑤(갱신) ⑥⑧(1회 산정) ⑦(하나의 질병) ⑩(감면), 제5조 ②(연간) ⑥(잔여 한도).

명령: `python -m coverage_extract <PDF> --gaps [--ground 데이터.json] [--out gaps.json]`.

## 19. 테이블 저장 (M8)

사고보장 JSON 을 관계형 테이블(SQLite)에 저장하고 다시 읽음. 업무 구조(상품 → 보장 → 위험률 → 지급 규칙 → 참조조건·급부·공제·특수조건·분할,
보상 제외, 담보코드 → KCD) 를 따르는 13개 테이블 + 참조조건 항목 사전 `condition_item`. 상세 DDL 은 [coverage_tables.md](coverage_tables.md).

- **모든 키에 product_id**: 규칙 id(`p0/질병급여형/…`)가 개정 전후 상품에서 같아서. 두 상품을 한 DB 에 넣고 rule_id 로 조인해 비교.
- **참조조건은 항목코드·값 한 줄씩** (`rule_condition`): `EXEMPT_DAYS`, `REDUCE_DAYS`/`REDUCE_RATIO_NUM`/`REDUCE_RATIO_DEN`,
  `DEDUCT_DAYS`, `LIMIT_EVENT_DAYS`, `LIMIT_TOTAL_DAYS`, `LIMIT_COUNT`, `LIMIT_AMT_<VISIT|DAY|STAY|YEAR|DAILY_AVERAGE|EVENT>`(selectable 컬럼),
  `EXT_DAYS`, `EXT_VISITS`, `EXT_VISIT_DAYS`. 규칙당 하나인 값(급부 유형·보상률·자기부담 상한·공제 선택)은 `benefit` 컬럼.
- **근거는 한 테이블** (`source_ref`): `target_type`(rule|exclusion|coverage|coverage_code) + `target_id`, `role`(primary|extra).
- 외래키 ON, CHECK(종류·상태), 상품 삭제 시 CASCADE. 같은 product_id 로 저장하면 지우고 다시 넣음(한 트랜잭션). 모든 목록 순서는 `seq`.
- 완료 기준: 실손 정답 → 테이블 → Product 가 원래와 같음, 행 수 product 1 · coverage 1 · coverage_code 5 · kcd_range 7 · risk 3 · exclusion 7 ·
  benefit_rule 4 · rule_condition 11 · benefit 4 · deductible 6 · special_condition 1 · installment 0 · source_ref 21 (=70행).
  스키마의 모든 필드를 쓰는 예시도 왕복이 같아야 함. 항목 사전에 없는 코드는 IntegrityError.

## 21. 설계 변경: 약관 → 보장 JSON 스키마 (M10, 2026-11-11)

**목표가 바뀌었습니다: 미리 정의한 스키마 `src/schema/json/coverage.json`(보장 하나의 모양)을 약관에서 뽑아내는 것.**
스키마와 약관 7개 분석은 [coverage_json_schema.md](coverage_json_schema.md) (스키마 파일·예시 2개도 같이 반입).
9장 사고보장 스키마(Product)는 중간 데이터로 계속 써도 되고, 최종 출력은 이 JSON 입니다.

### 21.1 흐름

```
약관 PDF → 텍스트(캐시) → 구조화(M1~M5) → 보장 묶음(10장) ─┬→ [AI] 조문 + 지급기준표 별표 + 스키마 → 보장 JSON 배열
                                                        │      → jsonschema 검증 → 틀리면 오류 붙여 재요청(2번) → 그래도 틀리면 맞는 항목만
                                                        └→ [API 없이] Product(정답·이전 추출) → 스키마 변환
                                                                          ↓
                                                        묶음별 캐시 → 약관 하나의 보장 JSON 목록 → (선택) 두 약관 비교
```

### 21.2 구현 요점

| 단계 | 할 일 | 함정 |
|---|---|---|
| 스키마 | `coverage.json` 은 표준 JSON Schema(draft 2020-12). `jsonschema.Draft202012Validator(schema, format_checker=FormatChecker())` 로 검증 | 팀 초안은 properties 목록만 있었음 → 최상위 `type: object` 로 감쌈 |
| 묶음 입력 | 10장 묶음 본문 + **그 약관 범위 안의 '보험금 지급기준표' 별표** (약관 제목 줄 번호 ~ 다음 약관 제목 줄 번호) | 정액형 지급 금액·1년 이내 감액은 조문이 아니라 별표1 에 있음 (20장) |
| 프롬프트 | 시스템: 출력은 `{"items": [...]}` 하나, 비율 0~1, 금액 원, 모르면 null/'판단불가', 보장 = 지급사유 하나, 실손은 보장종목 하나 = 보장 하나, 코드 판정 → `pgm_review_items`, 서류 판단 → `ai_review_items`, `source.quote` 는 원문 복사. 사용자: 스키마 JSON(설명 포함, `$schema`·`$id` 뺌, 약 1.4만 자) + 본문 | 스키마 설명에 예시를 넣어 두면(체증 일정, 분류질병별 1회 등) 모양을 잘 따름 |
| 검증·재시도 | 검증 오류(`[i] id 경로: 메시지`)를 20개까지 붙여 "고쳐서 다시". 마지막엔 오류 난 항목 번호만 빼고 남김 | 묶음 하나가 틀려도 다른 묶음은 살림 (동시 처리, 실패는 화면에 표시) |
| 캐시 | `data/cache/schema/<원본 파일 sha256 앞 16자>/<묶음>.json` = `{bundle, items, errors}`. 항목 0개면 저장 안 함(다음에 재시도) | 같은 PDF 를 다시 올려도 API 를 안 부름 |
| ID | `{회사}-{상품}-{약관}-{보장종목}-{보장}` (예: `SL-IND2605-MAIN-DIS-COV`, `SL-CA2404-MAIN-DX-1`) | 다시 뽑아도 같은 ID 여야 개정 비교 가능 |
| KCD | 분류표 범위(C00~C14) → 정규식 `^C(0[0-9]\|1[0-4])(\.[0-9]{1,2})?$`, 세분류(D47.1) → `^D47\.1[0-9]?$` | 코드로 못 가르는 분류(초기유방암 = C50 중 TNM 1기)는 `ai_review_items` 로 |
| 비교 | 보장 짝: 청구사유 같음 + 이름 유사도(괄호 안 대상 질병 포함, '(주계약)'·《》 만 뺌) + 보장종목 같으면 +0.5 + KCD 겹침 +0.3, 0.45 미만은 짝 없음. 필드(청구사유·KCD 수·면책·감액·보험금·실손 규칙·한도·제외 수) 나란히 | 이름에서 괄호를 다 지우면 소액암 24%/12% 가 뒤바뀜 |
