# 보장잇 약관 문서 구조화 설계

약관을 **원문 증거 → 업무 규칙 → 승인된 계산 규칙**으로 연결한다. 신상품 등록과 청구 심사는 동일한 보장ID와 규칙 버전을 사용한다. 문서의 해석이나 산식이 바뀌면 새 규칙 버전을 발행해 이전 심사 결과를 재현할 수 있도록 한다.

## 저장 구조

| 단위 | 주요 필드 | 역할 |
| --- | --- | --- |
| 약관 문서 | 문서 ID, 원본 SHA-256, 보험사, 상품, 문서 종류, 수집 경로 | 동일한 원본을 식별한다. 주계약, 특약, 별표가 별도 PDF일 수 있다. |
| 원문 조각 | 조각 ID, 문서 ID, PDF 페이지, 인쇄 쪽수, 조·항·호, 문단 또는 표 행·열, 원문, 좌표 | 본문·별표·각주의 위치와 읽은 값을 보존한다. PDF 페이지는 1부터 센다. 좌표에는 페이지 기준과 단위를 기록한다. |
| 적용 약관 | 상품 ID, 약관 버전, 적용 시작·종료일, 날짜 기준, 문서 목록 | 계약일, 갱신일, 전환일 등 해당 버전을 고르는 기준을 명시한다. 계약에서 적용할 버전을 확인할 수 없으면 검토를 보류한다. |
| 보장 규칙 버전 | 상품 ID, 약관 버전, 담보 ID, 보장ID, 규칙 버전, 지급 사건, 입력 정의, 조건, 지급액 산식, 근거 참조 | 담보 ID는 주계약이나 특약을 가리킨다. 한 담보 아래 진단·수술·입원 등 여러 보장ID를 둘 수 있다. |
| 승인·실행 이력 | 검토자, 시간, 상태, 변경 이유, 규칙 버전과 해시, 검증 결과 | 승인 대상과 적용한 규칙을 추적한다. 개정 이후에도 과거 심사에서 선택한 규칙 버전을 조회할 수 있게 한다. |

해커톤 SQLite에서는 문서, 원문 조각, 약관 버전, 규칙 버전, 승인 이력을 관계형 테이블로 관리한다. 조건·산식·분류표 참조는 규칙 버전의 JSON으로 저장한다. 동일 원본 재업로드는 SHA-256으로 감지한다. 보장ID는 한 상품 안에서 동일한 지급 의미를 식별하고, 실제 적용 키는 `상품 ID + 약관 버전 + 담보 ID + 보장ID + 규칙 버전`이다.

## 원문에서 승인까지

1. **문서 등록 및 추출.** Streamlit에서 약관을 등록하고 텍스트와 표를 페이지별로 추출한다. 스캔은 OCR 경로로 분리한다. 표의 병합 셀, 반복 머리글, 각주, 페이지 경계를 복원하고 판독 불가 부분을 표시한다.
2. **조항 연결.** 본문 조항, 분류표, 지급기준표, 각주에 조각 ID를 부여한다. 예를 들어 본문의 지급 사유가 별표 1과 별표 3을 참조하면 두 참조를 연결한다. 대상 별표가 없거나 조항 번호가 여러 후보와 일치하면 검토 항목으로 남긴다.
3. **규칙 초안 생성.** AI는 허용된 규칙 형식에 맞춰 지급 사유, 분류 기준, 면책·감액, 횟수·금액 한도, 산식 초안을 제안한다. 조건마다 근거 조각을 붙이고, 조항과 표의 충돌이나 빠진 변수는 별도 목록으로 표시한다.
4. **검증 및 승인.** JSON Schema로 구조를 검증한다. 도메인 검증에서는 참조가 실제로 존재하는지, 변수 단위가 일치하는지, 조건이 겹치거나 빠지는지 확인한다. 전문가가 원문과 경계 사례를 확인한 뒤 승인한다. [JSON Schema 2020-12](https://json-schema.org/draft/2020-12)
5. **배포 및 이력.** 승인된 규칙만 지급시스템으로 내보낸다. 승인된 내용을 바꾸려면 새 초안을 만들고 다시 검토한다. 이전 버전이 신규 적용 대상에서 빠져도, 그 버전을 사용한 기존 심사 기록의 재현에는 사용할 수 있게 보관한다.

Streamlit 검토 화면은 한쪽에 원문 페이지·표 셀을, 다른 쪽에 정규화 값·조건·산식을 표시한다. AI가 제안한 값과 담당자가 수정한 값을 분리하고, 상태는 `draft → reviewed → retired`로 관리한다. `reviewed` 전환과 검토 이력 기록은 한 트랜잭션으로 처리한다.

## 규칙 JSON 예시

가상 계약의 암 진단급부 예시다. ID와 지급률은 형식을 설명하기 위해 정한 값이다.

```json
{
  "schema_version": "1.0",
  "product_id": "demo-cancer",
  "policy_version": "demo-v1",
  "coverage_group_id": "main",
  "coverage_id": "cancer-diagnosis",
  "rule_version": 1,
  "status": "draft",
  "event": "confirmed_diagnosis",
  "classification_ref": "demo-v1/cancer-codes",
  "conditions": [
    {
      "id": "coverage_started",
      "op": "date_gte",
      "left": "diagnosis_confirmed_on",
      "right": "coverage_starts_on",
      "source_refs": ["demo-v1/clause-3"]
    },
    {
      "id": "first_eligible_diagnosis",
      "op": "is_true",
      "input": "first_eligible_diagnosis",
      "source_refs": ["demo-v1/clause-5"]
    }
  ],
  "payout": {
    "op": "multiply",
    "input": "sum_insured_krw",
    "factor": "0.50",
    "currency": "KRW",
    "rounding": "floor_won",
    "source_refs": ["demo-v1/annex-1/row-2"]
  }
}
```

예시의 `coverage_starts_on`은 계약 조건에서 가져오는 입력이다. 실제 약관에서 날짜 산식을 추출할 때는 기준일, 기간 단위, 기준일 포함 여부, 비교 연산, 존재하지 않는 계약해당일의 처리 기준까지 구조화한다. 횟수 한도에는 집계 범위와 갱신 시점을, 금액 산식에는 통화·단위와 반올림 적용 단계를 둔다.

산식은 허용된 연산과 타입이 정해진 입력의 조합으로 해석한다. 지급 조건은 충족·미충족·정보 부족으로 평가한다. 예외나 조항 충돌로 적용 순서를 확정할 수 없으면 결과에 그 이유를 남기고 금액 계산을 보류한다. 금액은 Python `Decimal`로 계산한다.

## 청구 AI 태그와의 연결

진단서에 코드가 있으면 **서류에서 읽은 사실**로 남기고, 가입 계약의 약관 분류표와 일치하면 별도의 **분류 후보 태그**를 생성한다. 초기암 요건에 필요한 병기·침윤 등 증빙이 빠졌으면 `정보 부족`과 필요한 자료를 표시한다. 소액암 후보는 상품·약관 버전·보장ID에 귀속시킨다. 태그와 계산 결과에는 청구 서류 원문 위치, 약관 근거, 사용한 규칙 버전과 조건별 판단을 함께 기록한다.

첫 구현은 암 진단급부 한 건을 대상으로 한다. **원문 업로드 → 조항·별표 연결 → 규칙 초안 → 전문가 검토 → 가상 청구 태그와 계산 근거**까지 연결한 뒤 5세대 실손으로 확장한다. 첫 검증에는 별표 누락, 지급표와 각주 충돌, 개시일 전날·당일, 진단 증빙 누락, 개정 전후 분류 변경을 넣는다.

현재 보장잇의 정액보험 초안과 실손 시뮬레이션은 이 구조의 입력 사례로 활용한다. [정액보험 초안](../apps/web/src/fixed-benefit-policies.json) · [실손 계산 예시](../apps/web/src/indemnity-outpatient.ts)
