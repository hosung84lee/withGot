# 보장잇 개인정보 보호 중심 구현계획

작성일 2026-11-07. 각 단계의 완료 기준으로 구현 결과를 확인한다. 첫 시연 구현과 검증 범위는 README.md와 VERIFICATION.md에 기록한다.

## 목표와 첫 시연 범위

사용자가 원본 서류를 기기에 둔 상태에서 치료 항목을 검토하고, 보장 후보 조회에 필요한 항목만 확인하여 서버로 보낸다. 원본의 해당 위치와 조회 결과를 같은 화면에서 확인한다.

첫 입력은 직접 만든 가상 영수증·세부내역서 한 쌍이다. 텍스트가 포함된 PDF와 정해진 서식만 지원한다. 스캔 PDF·사진·병원별 다양한 서식은 별도 추출 단계에서 다룬다. 지원하지 않는 문서는 이유를 표시하고 검토 단계에서 멈춘다.

첫 출력은 가상 계약에 대한 보장 후보와 추가 확인 항목이다. 실제 약관 판정과 보험금 계산은 전문가가 검토한 규칙과 정답 사례를 확보한 뒤 연결한다. 시연용 규칙에는 별도 식별자와 가상 사례 표시를 둔다.

## 구현 착수 전 확인한 사항

- apps/web/src/main.tsx는 가상 치료 목록과 파일명 선택을 제공한다. 파일 내용 추출과 API 조회는 아직 없다.
- apps/api/app/main.py는 상태 API만 제공한다.
- apps/web/src/style.css는 Google Fonts를 외부에서 불러온다.
- pdfjs-dist가 의존성에 포함되어 있으나 소스에서 사용하지 않는다. 이전 설치 감사에서 확인한 보안 문제를 해결한 뒤 PDF 읽기를 연결한다.
- scripts/preview.py는 빌드 파일만 제공한다. API 프록시는 Vite 개발 서버에 설정되어 있다.

## 이전 제안에서 보완한 결정

1. 개인정보 검출보다 전송 데이터 구성을 먼저 제한한다. 검출 누락이 있어도 이름·파일명·원문·자유 입력이 요청에 섞이지 않게 한다.
2. 치료 종류와 금액도 민감한 정보로 취급한다. 이름 제거를 익명화 완료로 표현하지 않는다.
3. 필요한 서버 처리를 구체화한다. 브라우저는 추출·검토·원본 위치 표시를 담당하고, API는 승인한 구조화 항목으로 가상 규칙 버전에 따른 보장 후보를 조회한다.
4. 검토 화면과 전송 요청은 동일한 불변 스냅샷을 사용한다. 수정 후에는 검토를 다시 거친다.
5. 원본 보관과 로그 보관을 각각 검증한다. 오류 응답과 브라우저 저장소도 검사 대상에 포함한다.
6. 통신 보호 주장을 범위와 함께 제시한다. 사용자의 승인 전 문서 데이터 전송 차단, 승인 후 허용 필드 전송, 제3자 문서 전송 차단을 각각 검증한다.

## 처리 경로와 상태

파일 선택 → 기기 내 추출 → 사용자 검토 → 전송 내용 확인 → 서버 조회 → 보장 지도·기기 내 원본 확인.

상태는 idle → extracting → review_required → ready_to_send → sending → result로 둔다. 추출 실패는 review_required 이전의 오류 상태로 돌아가고, 요청 실패는 검토한 스냅샷을 보존해 사용자가 재시도할 수 있게 한다.

새 파일 선택, 항목 수정, 선택 해제, 계약 조건 수정 시 전송 확인을 초기화한다. 중복 클릭 동안 요청 버튼을 잠그고, 초기화·새 파일 선택 시 진행 중 요청과 추출 작업을 취소한다. 이미 시작된 요청의 전송을 되돌릴 수 있다고 표현하지 않는다. 이전 작업의 늦은 응답은 현재 화면에 적용하지 않는다.

원본 바이트·추출 원문·파일명·페이지 위치는 브라우저 메모리에서만 관리한다. 해당 위치는 문서·페이지·좌표 또는 텍스트 범위로 보존하고 서버 응답의 항목 식별자를 이용해 기기 내 원본과 연결한다.

## 전송 계약 초안

요청은 아래에 정한 필드로 새로 구성한다. 추출 객체를 복사한 뒤 일부 필드를 지우는 방식은 사용하지 않는다.

| 필드 | 허용 범위와 용도 |
| --- | --- |
| 항목 식별자 | 요청 내 순번. 이름·환자번호·원본 해시에서 생성하지 않음 |
| 치료 종류 | 시연에서 지원하는 고정 열거형. 진찰·혈액검사·MRI·주사 |
| 급여 구분 | 급여·비급여·미확인 열거형 |
| 가상 계약 조건 | 선택한 치료에 필요한 담보별 가입·미가입·미확인 열거형. 급여 구분이 미확인인 항목은 담보 상태 없이 조회 |
| 규칙 버전 | 서버에서 허용한 가상 규칙 버전 |

알 수 없는 치료명·병원 자체 코드는 기기에서 검토 대상으로 남긴다. 총액과 환자 부담액은 기기에서 구분해 대조하며, 현재 가상 규칙의 웹 요청에는 금액을 포함하지 않는다. 기존 API 호출 형식의 금액 쌍은 호환성을 위해 검증한다. 날짜·병원명·진단명은 첫 조회 규칙에 필요하지 않으므로 요청 계약에서 제외한다. 이후 실제 규칙에 필요해지면 사용 목적과 전송 화면을 함께 변경한다.

API는 최상위와 중첩 객체 모두 알 수 없는 필드를 거절하고, 자료형·항목 수·본문 크기·금액 범위를 검사한다. 오류 응답에는 고정 오류 코드와 허용된 필드 경로만 반환한다. 입력값·본문·예외 내부 정보를 오류에 반영하지 않는다.

응답에는 요청의 항목 식별자, 보장 후보, 추가 확인 항목, 가상 규칙 버전을 포함한다. 브라우저 원문과 사용자 수정값은 별도로 보존해 수정 출처를 표시한다.

## 구현 순서와 완료 기준

| 단계 | 구현 범위 | 완료 기준 |
| --- | --- | --- |
| 1. 실행 기반과 계약 | PDF 의존성 보안 문제 해결, 폰트 로컬 제공 또는 시스템 글꼴 사용, 요청·응답 모델과 가상 규칙 정의 | 잠금 파일 기준 설치·검사 통과. 제3자 자산 요청과 서버의 업스트림 문서 전송 없음 |
| 2. 기기 내 추출 | PDF 읽기, 지원 서식 파싱, 원본 위치 저장, 파일 검증 | 가상 한 쌍의 항목과 원문 위치 일치. 미지원·손상·암호화·제한 초과 파일의 오류 처리 |
| 3. 사용자 검토 | 항목 수정·선택, 비용 의미 표시, 영수증 환자 부담액 대조 | 선택 변경이 합계와 전송 후보에 반영됨. 불일치·불완전 추출을 숨기지 않고 전송 전 검토 필요 상태로 표시 |
| 4. 전송과 보장 지도 | 전송 스냅샷 확인, 명시적 조회 버튼, 엄격한 API 입력 검증, 가상 후보 응답, 원본 위치 강조 | 화면에서 확인한 내용과 실제 요청 일치. 검토한 항목만 조회. 이전 작업 응답 혼입 방지 |
| 5. 종료와 검증 | 세션 초기화, PDF 작업·요청 취소, 객체 URL 해제, 로그 검사, 시연 자동화 | 초기화 후 앱 상태와 앱이 사용하는 저장소에서 문서 데이터 제거. 아래 보호 기준 통과 |

각 단계는 독립적으로 시연 가능한 상태에서 마친다. 실제 약관의 전문가 검토가 완료되면 가상 조회와 구분하여 연결한다.

PDF 입력 제한은 첫 구현에서 파일당 10 MiB, 10페이지, 한 번에 2개로 시작한다. 제한값은 성능 측정 후 조정한다. 확장자와 MIME 확인에 더해 PDF 헤더·파싱 결과를 확인하고, 파싱 시간 제한과 취소 처리를 둔다. 외부 링크·문서 스크립트·첨부파일 실행은 차단한다.

## 개인정보 보호 검증

가상 이름과 추적용 문자열을 파일명·본문에 각각 삽입해 검사한다. 아래 검증은 실제 의료 서류 없이 수행한다.

- 파일 선택·추출·수정·검토 과정에서 문서 데이터가 포함된 요청이 발생하지 않는다.
- 실제 화면과 파일 선택 경로를 사용한 브라우저 테스트에서 승인한 요청 본문만 발생한다. 원본 바이트, 파일명, 추적 문자열, 자유 입력이 포함되지 않는다.
- 브라우저에서 외부 OCR·LLM·분석 도구로 문서 데이터가 전송되지 않는다. 서버의 외부 HTTP 호출 경로도 확인한다.
- 예상하지 않은 개인정보 필드를 최상위·중첩·유효하지 않은 열거형 값에 넣으면 API가 거절한다. 거절 응답·성공 응답·서버 로그·오류 로그에 입력값이 반사되지 않는다.
- 서버는 요청 본문과 문서 데이터를 저장하지 않는다. 로그는 생성한 요청 ID·허용한 경로·고정 상태 코드 중심으로 기록한다. 파일명·본문·쿼리 문자열을 로그 항목으로 사용하지 않는다.
- 항목 수정 후 기존 전송 승인이 무효화된다. 네트워크 실패·중복 클릭·초기화 중 응답 도착을 검사한다.
- localStorage·sessionStorage·IndexedDB·서비스 워커 캐시에 원본과 추출 내용을 저장하지 않는다. 서버와 중간 프록시의 응답 캐시 정책도 확인한다.
- 브라우저의 세션 초기화 후 원본 미리보기와 분석 결과가 사라지고, 객체 URL과 PDF 작업이 해제된다. 브라우저·OS 메모리의 물리적 완전 삭제를 보장한다고 표시하지 않는다.

필수 개발 검사는 기존 Ruff·pytest·TypeScript·Vite 빌드를 사용한다. 추가 테스트는 위 개인정보 경계와 사용자 전송 흐름의 회귀를 잡는 데 집중한다.

## 실행·배포 경계

첫 완료 환경은 로컬 Vite와 FastAPI다. 배포 시 프런트와 API의 동일 출처 경로, HTTPS, 허용 출처 정책, 요청 본문 수집을 끈 프록시·오류 수집 설정을 확인한다. CSP는 PDF 워커와 실제 자산을 기준으로 제한하고, Vite 개발용 연결은 운영 정책에서 분리한다.

공개 해커톤 시연은 가상 자료를 사용한다. 실제 의료 자료를 받는 배포 단계에서는 사용자별 접근 통제, 보관·삭제 정책, 운영 로그와 인프라 설정 검토를 별도 완료 조건으로 둔다.

## 시연 순서와 주장 범위

1. 가상 이름·환자번호가 있는 샘플 한 쌍을 선택하고 네트워크 요청을 확인한다.
2. 추출한 MRI 항목의 원본 위치를 확인하고 급여 구분을 검토한다.
3. 서버로 보낼 항목과 목적을 확인하고 조회한다.
4. 네트워크 요청에서 허용한 항목만 전송되었음을 확인한다.
5. 보장 지도에서 가상 담보 후보와 추가 확인 항목을 확인하고 원본의 같은 줄을 연다.
6. 세션을 초기화하고 화면과 앱 저장소를 확인한다.

발표에서는 지원 PDF 범위, 기기 내 처리 항목, 실제 전송 항목, 저장 정책, 자동 검증 범위를 함께 제시한다. 관찰한 요청과 테스트 결과로 개인정보 보호 설계를 설명한다.

## 후속 확장

기기 내 OCR과 다양한 서식 지원 → 전문가 검토 약관·계약 연결 → 규칙에 필요한 추가 정보의 목적별 전송 → 검토된 계산 규칙 적용 순으로 확장한다. 각 확장에서 전송 계약과 원본 위치 정확도, 누락 처리, 검증 사례를 함께 갱신한다.
